# 设计取舍

这份文档记录「为什么这么做」，而不是「做了什么」（功能见 [README](../README.md)）。
里面每一条都对应代码里的注释；这里把散落的理由收成一份可通读的版本。

---

## 一、窗口

### 无边框窗口：标题栏的职责要有人接

`tauri.conf.json` 里 `decorations: false`，系统标题栏不存在，于是它的职责全部落到界面上：

- **拖动与双击最大化**：顶栏挂 `data-tauri-drag-region="deep"`。这是 Tauri 的语义 ——
  整个子树都能拖，但按钮/链接/输入框这类可点击元素会自动阻断拖拽，
  所以不用给每个控件加例外。双击走的是 Tauri 内建的 `internal_toggle_maximize`。
- **最小化 / 最大化 / 关闭**：自绘按钮，图标用同一套 Lucide，hover 反馈跟界面一致
  （关闭键是唯一用红色 hover 的控件：误点代价最大）。最大化与还原是同一个按钮，
  图标跟着 `onResized` 事件走 —— 从系统侧改状态（双击顶栏、`Win+↑`、拖到屏幕顶贴边）也同步。
- **缩放**：8 个方向的透明热区 + `startResizeDragging`，把方向交给系统去做真正的缩放循环。
  自己算尺寸会在拖动时抖动，而且贴边（Aero Snap）逻辑会失效。

一个安全阀：把 `decorations` 改回 `true` 就能退回系统标题栏，其余功能不受影响。

### 全屏毛玻璃：两层，缺一层就白做

1. **系统层**：窗口 `transparent: true` + `windowEffects: { effects: ["acrylic"] }`（DWM 负责模糊窗口后面的桌面）；
2. **界面层**：把界面底色换成半透明（`--paper-alpha` / `--ui-content` / `--ui-chrome`）。

只做第 1 层是没用的：界面不透明，玻璃后面什么都看不见。
三挡（关闭 / 中等 / 强）只差三组不透明度数字。

**一个绕不过去的平台限制**：Windows 上窗口一旦 `transparent: true`，
Chromium 就**不再执行 `backdrop-filter`**（[tauri#12804](https://github.com/tauri-apps/tauri/issues/12804)、
[#12986](https://github.com/tauri-apps/tauri/issues/12986)、
[wails#2340](https://github.com/wailsapp/wails/issues/2340) 都是这个结论）。
于是「全屏玻璃」与「顶栏模糊从它下面滚过的正文」在 Windows 上**互斥**：

- 玻璃挡位下顶栏能依靠的只有系统 acrylic（模糊的是窗口后面的桌面）。
  既然拿不到内容模糊，就让正文**裁在界面层下方**
  （`.pane-preview` 的 `clip-path: inset(--top-offset 0 --bottom-offset 0)`）——
  让未模糊的正文从玻璃条下面划过去，只会看起来像脏了一条，比裁掉更难看。
- 「关闭」挡位不透明、也不裁，正文照旧从界面层下穿过。
- zen 下 `--top-offset` 为 0，等于不裁；此时界面层浮在正文之上，
  没有模糊就更要靠底色压住文字，所以 zen 唤出时玻璃条的不透明度提到 0.94。

这里还踩过一个坑，值得记下来：**叠加的半透明层，透明度是相乘的**。
`.workspace`（0.80）里面又套 `.pane-preview`（0.84），两层叠完只剩 3% 的背景能透出来，
看上去和纯白没区别（实测 RGB 253 → 249，肉眼不可辨）。现在玻璃模式下
`.workspace` 主动让出底色，由面板自己铺一层半透明，实测 253 → 232（中等）/ 212（强）。

不透明度刻意取得偏保守（中等纸面 0.88 / 强纸面 0.76）：
acrylic 在部分 Win10 上不可用，那时窗口就是「半透明糊在桌面上」，底色太透会直接读不了字。
「关闭」挡位不需要撤销系统效果 —— 把界面画成不透明，后面那层模糊自然就看不见了，
少一次可能失败的运行时调用，也少一种状态。

### 自绘标题栏的两个坑

- **窗口控制按钮不能是可压缩的 flex 项**。最初 `.win-controls` 只是 `display: flex`，
  默认 `flex-shrink: 1`：窗口一窄，三个按钮一起被挤扁，
  表现为「最小化和关闭还看得见，中间那个方框没了」—— 方框全靠 1px 描边，最先消失。
  现在 `flex: none` + `min-width: 44px`，图标也改用对比度最高的 `--fg`
  （玻璃挡位下这些按钮的背景可能是任意桌面，次要灰会糊掉）。
- **拖动区域必须用 `drag-region="deep"`**：裸属性在 Tauri 里只认「直接点在它身上」，
  而顶栏大部分面积被子元素盖住，那样几乎拖不动。`deep` 让整棵子树都能拖，
  同时按钮/链接/输入框会自动阻断拖拽，不必逐个加例外。


### 语言

`navigator.language` 在 WebView2 里就是 Windows 的显示语言，所以「跟随系统」不需要任何原生调用。
一张词表 + `t()` 就够了，没有引入 i18n 库：两种语言、没有复数/性别/日期本地化需求，
库反而是首屏体积加一层运行时。

两个实现上的细节：
- 主题与字体的名称/说明在数据文件里成对存在（`label`/`labelEn`），
  渲染时用 `pick()` 取 —— 卡片、状态栏、下拉项都共用一处真相；
- 切语言要重刷三类东西：`index.html` 里的静态文案（`data-i18n` 属性）、
  动态渲染的（标签/状态栏/大纲）、以及设置面板本身（开着就重画）。

英文界面下会关掉为中文调的排版（字距 0.02em、两端对齐）——
那些规则是给方块字调的，套在拉丁文本上只会显得字距怪异。

## 二、界面

### 默认进入阅读视图

打开文件直接看到渲染好的文档，编辑器完全隐藏 —— 这是阅读器的本分。
CodeMirror 全家桶 575 KB，而 `.group.is-read` 下编辑器面板本来就是 `display:none`，
启动时创建它、再把整篇文档灌进去做语法解析，对「只是读一份文档」是纯浪费。

### 设置是右侧抽屉，不是全屏模态框

全屏模态会遮住文档，而**设置的意义恰恰是「边调边看」**：换主题、调字号、改行高，
效果必须立刻看得见。所以抽屉展开时顶栏、工作区、状态栏一起收窄。

### 设置分两级：抽屉放高频，模态放低频

抽屉必须短到一眼扫得完 —— 它不是一个「设置大全」，而是**边调边看的那几件事**：

| 层级 | 内容 | 为什么在这 |
|---|---|---|
| 抽屉（常用） | 正文主题、正文字体、文字大小、最近打开 | 每天都会动；调完立刻在左侧文档里看得见 |
| 高级设置（模态） | 排版细节、窗口与界面、行为、文件关联、快捷键 | 一年动不了一次，常驻只会把高频项稀释掉 |

分级的直接动机是旧版的失败：六张等权重的分区卡挤在同一列里，找一个滑杆要往下滚三屏。
**低频项不是不重要，而是不该和主题抢第一屏。** 底部那条「高级设置」入口是常驻横幅，
不埋在滚到底之后 —— 否则「找不到行高在哪」会变成新的问题。

抽屉的四个分区是有主次的：主题是主角，字体与字号是配角，最近打开是「找文件」而不是
「调外观」，所以放在最后（打开文件本来就有 `Ctrl+O`、顶栏按钮和空状态三个入口）。
条目仍可逐个固定（图钉）或移除，「清空未固定」不会带走固定项。

### 主题预览：把「主题的颜色」和「界面的颜色」分开

旧版主题卡片的毛病不在信息不够，而在**边界不清**：预览区正下方直接贴着一条界面白底的
说明栏（主题名 + 一句话说明），看上去就像「这个主题是白的」—— 用户抱怨的正是这一点。

现在分成两层，各解决一件事：

1. **样板页**：选中的那款主题给足尺寸（约 384 × 142），真正按该主题渲染一段文档
   （标题 / 正文 / 强调 / 链接 / 行内代码 / 引用块 / 代码块），它被摆在一块界面色
   （`--ui-sunken`）的衬底上，纸面只占中间一块。四周那一圈「衬底」就是界面自己的颜色，
   谁也误认不了；再配一个「主题预览」的角标，把这块区域的性质写在脸上。
2. **色板**：纸面 / 正文 / 标题 / 强调 / 引用五个真实取色圆点。配色这种事，与其让用户
   从一段样例文字里猜，不如把色值本身摆出来 —— 描边走界面自己的前景灰，因为纸面可能
   是近白色，用主题自己的 `--rule` 会在这块浅底上消失。
3. **其余主题用色块比色**：每块只画「纸面 + 标题条 + 正文条 + 强调条 + 引用块」。
   12 款三行排得下，不用在小框里塞一段读不清的字；名字与说明一律落在界面底色上。

样板页仍然走 Shadow DOM + 只注入该主题的 CSS 变量：13 个主题互不污染，
也不会把主题样式漏进主界面。

### 毛玻璃要靠布局配合才成立

顶栏、标签条、状态栏、大纲侧栏、设置抽屉都用了 `backdrop-filter`。
关键在于**布局结构**：它们是 `position: absolute` 叠在工作区之上，工作区占满整窗。
如果工作区只是 grid 里的一行（兄弟元素），毛玻璃什么也模糊不到 ——
必须让内容真正从玻璃层下方「滚过去」。

层次由三部分组成：半透明底色 + `blur(20px) saturate(150%)` + 内侧高光边与投影。
底色不透明度是**对比度的下限**：浅色 0.62 / 深色 0.76（`--glass-bg`），再低文字就会糊。
设置里留了 `solid / normal / strong` 三档，给关掉系统透明效果的用户一个退路。

由此派生出一条容易被忽略的规则：**正文的顶部留白必须跟着 `--top-offset` 走**。
顶栏 46 + 标签条 34 = 80px，早期写死 56px，加标签条之后第一行正好落在玻璃底下，
看上去像空白页。

### 分组 → 标签：两层结构

- **分组**是一块独立的阅读区：自己的标签列表、自己的视图模式、自己的编辑器实例。
  默认只有一块；拖文件（或拖标签）到某一栏的侧档才会出现第二块，最多三块。
  键盘、工具栏、大纲作用在**当前分组**上，非当前那一栏的标签条整体降一档。
- **标签**是一份文档。同一栏里已打开过的文件直接切过去，不会开第二份。
  标签名取 H1，退而求其次取正文前 16 字，最后才是文件名 —— 读者记住的是标题，不是文件名。
- 每栏一个 CodeMirror 实例：切标签时正文与撤销历史跟着换，不是一份全局状态。

### 拖到哪，就在哪开：落点和提示必须出自同一份几何

旧版把「落点判定」与「提示画面」各算各的：提示是 `inset: 0` 的**整窗三等分**（于是盖住了顶栏与
大纲侧栏 —— 那两处根本不是内容区），判定是「鼠标 x 落在窗口宽度的哪一段」。没分栏时凑合能用，
一分栏立刻错位：中间那一档横跨两栏，提示画在 A、松手落到 B。

现在只留一个真相来源：

- **提示层只铺内容区**：左边界取 `.groups` 的左边界（大纲侧栏是它的兄弟节点，天然被排除），
  上边界取标题栏的 `bottom`（zen 里标题栏滑出视野，量出来自然是 0），下边界按 `--bottom-offset`
  退掉状态栏。硬编码那 46px 在 zen 下会留一条空档。
- **每一栏一张卡片**，卡片的 left/top/width/height 直接取那一栏的 `getBoundingClientRect()`；
  卡片内部再切左 / 中 / 右三档。
- **命中判定拿指针去撞已经渲染出来的 `.dz` 矩形**，不再自己算百分比。

于是「看到的」与「会发生的」不可能再对不上 —— 不是靠两边小心翼翼地写同一个公式，
而是结构上只留了一份公式。

### 分栏现状决定有几档

| 当前分栏 | 每一栏提供的档位 |
|---|---|
| 1 栏 | 左 1/4 在左侧新开一栏 · 中间在这一栏打开 · 右 1/4 在右侧新开一栏 |
| 2 栏 | 每栏各自三档：落在哪一栏的中间就进哪一栏；落在某一栏的边上，就在**那一栏旁边**插一栏 |
| 3 栏（上限） | 每栏只剩「中间」一档 |

上限 3 栏；内容区宽度不足以让每栏留到 320px 时也不再提供分栏档。
**不画一个自己兑现不了的承诺** —— 这个判断（`canSplitNow()`）同时决定提示层画几档、命中判定认几档。

### 标签也能拖：两种语义，一套落点

同栏里的两个标签怎么变成左右分栏？拖标签头即可 —— 拖动标签时复用上面那套落点，
只是松手后兑现的动作从「打开文件」换成「搬运标签」：

- 中间 → 整条标签移到那一栏；
- 左侧 / 右侧 → 以这条标签为新栏的内容，在那一栏旁边分栏（这就是「两个标签 → 左右分栏」的路径）；
- 落回它自己那一栏 → 不动。这一档特意**不高亮强调色**，文案写「留在原处」：
  让「松开不会变」也是一个确定的结果，而不是让人怀疑是不是没生效。

用 HTML5 拖放（`draggable` + `dragstart` / `dragover` / `drop`）而不是自己撸 pointer 事件：
被拖的东西本来就是 DOM 节点，浏览器的拖影、光标、起拖阈值都是现成的，也不会和点选、中键关闭打架。
按在标签的 × 上往外拖会被拦下 —— 那是「关标签」的手势。

搬运本身（`moveTabToGroup`）有三个必须自己处理的点：

1. 编辑器是**每栏一个 CodeMirror 实例**：搬之前先把源栏编辑器的内容写回标签，
   否则正在编辑的那几个字会跟着源栏一起蒸发；
2. 源栏空了就整栏收掉 —— 这既是「取消分栏」的自然路径，也保证不会留下没有任何标签的空壳栏；
3. 目的栏已经开着同一个文件时不搬，否则同一栏会出现两个指向同一文件的标签。

### 落在内容区之外

指针不在任何一档上（顶栏、大纲、状态栏、窗口外）时命中为 null：文件按「打开到当前栏」处理
（拖进窗口本来就该打开），标签原地不动（等于取消）。

### 一次拖入多个文件

第一份决定落点（要不要分栏、分到哪一侧），其余依次开成同一栏的标签。
旧版只取 `paths[0]`，拖 5 个文件会静默丢掉 4 个。

### Zen：只在边缘「露出一条缝」

界面层不是被 `display:none` 掉的，而是滑出视野（`opacity` + `transform`）——
它们仍然是浮层，所以**唤出时正文不会重排**。鼠标到上缘 / 左缘 / 下缘时对应那层滑回来。

进入 Zen 会去掉系统标题栏；**窗口本来最大化就直接切真全屏** ——
最大化仍然留着一条窗口边框与标题栏区域，和「全是内容」是矛盾的。
因为标题栏没了，顶栏带上了 `data-tauri-drag-region`，仍可拖动与双击最大化/还原。

### 缩放的真相是一个系数

「放大 / 缩小」不是把字号调大，而是给整个版面乘一个系数（`--mr-zoom`，50%–300%，13 个等比档位）。

字号、行宽、正文留白、编辑区字号都写成 `calc(基准 × --mr-zoom)`，正文内部的标题、代码块、
表格、引用走 `em`，于是自动跟随。这样做有两个好处：

- 设置里的「正文字号」始终是**基准值**。放大 150% 之后再调字号，调的仍是基准，
  屏幕上实际大小 = 基准 × 系数，不会在放大后的数字上再叠一层；
- 缩放前后**每行字数不变**（行宽与字号同倍变化），观感与浏览器 `Ctrl+=` 一致 ——
  整块版面变大，而不是「同一栏里字变大、每行只剩八个字」。

导出 PDF 不受影响：打印样式表把字号钉在 11.5pt、行宽铺满纸面。

### 主题明暗靠实测，不靠文件名猜

正文主题的明暗不是写死在配置里的猜测。深色主题的纸面色由 `theme.css` 给出，
界面明暗默认跟随正文主题的深浅（`uiDark: null`），用户手动切过之后才不再跟随。

## 三、字体：为什么不惜体积

中文阅读器最容易露馅的地方是字体。系统回退会让同一段文字出现两种字形，
而 `Noto Sans SC` 这类思源字体的字符集才是「任何汉字都长一个样」的保证。

| 字体 | 码位数 | 中文 | 数学符号 | 箭头 | 全角标点 |
|---|---|---|---|---|---|
| Noto Sans SC | 30,890 | ✓ | ✓ | ✓ | ✓ |
| Noto Serif SC | 30,928 | ✓ | ✓ | ✓ | ✓ |
| Inter / Garamond / Mono | ~230 | ✗ | ✗ | ✗ | ✗ |

西文字体只有两百多个码位，只能当**装饰**放在字体栈前面。
任何它没有的字符都由 Noto SC 接住 —— 这就是为什么回退链里 Noto SC 是必选项：

```
'Eunice Inter', 'Eunice Sans SC', 'Segoe UI Symbol', 'Segoe UI Emoji', sans-serif
```

浏览器**按单个字符**逐一回退，于是「西文用 Inter + 中文用思源黑体」自动成立。
`Segoe UI Symbol` 兜住 Noto SC 也没有的 ✔✗✘，`Segoe UI Emoji` 兜 emoji，
两者都是 Windows 自带，不增加体积。

**关于子集化**：试过把字体裁到 GB2312 + 常用符号（7,658 字，体积省 26%），
但生僻字仍会掉进系统回退、字形突变。个人自用、体积无所谓，
因此直接内置完整字符集，**任何汉字都不会 fallback**。

霞鹜文楷采用 `unicode-range` 分片（194 片，共 8.8 MB），运行时只加载文档里真正用到的分片，
约 100–250 KB。`scripts/slice-fonts.py` 生成时会断言「三层并集 == 原字体 cmap」，
所以分片不会悄悄丢字。

## 四、Windows 集成

### 文件关联：ProgId 只有一个

`tauri.conf.json` 的 `fileAssociations[].name`（`Markdown Document`）就是 Tauri 的 NSIS
模板用来建类的名字，并把它自己的 `DefaultIcon` 写成 exe 图标。所以安装钩子必须
**覆盖在这同一个类上**，把图标换成 `icons/file-markdown.ico`。

写到别的 ProgId 上等于没写：Windows 解析 `.md` 图标时，只看 `UserChoice` /
`.md` 默认值指向的那个类。这一条踩过坑 —— 早先另起了一个 `EuniceReader.Markdown.1`，
结果图标永远是 app 图标。

### 默认应用改不了，只能请用户确认

Windows 8 起默认应用由 `UserChoice` 决定，它带哈希校验，第三方写入会被系统忽略。
安装器能做的是把本程序登记成候选：

- `Applications\eunice-reader.exe` + `FriendlyAppName` → 「打开方式」里显示名字而不是裸 exe 文件名；
- 9 个扩展名的 `OpenWithProgids`（值名必须是 **ProgId**，早期这里写成 exe 名，列表里就成了裸 exe）。

剩下那一步交给用户：设置面板的「文件关联」显示当前 `.md` 的默认程序，
未指向本程序时一键跳到系统「默认应用」页面。

### 注册内容带版本

`HKCU\Software\EuniceReader\assoc_version` = 程序版本 + `ASSOC_REVISION`（见 `lib.rs`）。
只改注册逻辑而不改这个数字，已经装好的机器永远等不到新内容。
安装钩子与 Rust 的 `register_open_with` 写的是**同一套键**：前者管新装的机器，
后者管「安装包已装好、只升级了程序」的机器。写 HKCU 而非 HKLM，与 `installMode: currentUser` 一致。

### 编码处理

读取时 UTF-8 优先，检测 BOM；解码失败回退 GB18030 → GBK → Big5（看 `had_errors`，
否则 GB18030 会把 Big5 文档也吞掉）。状态栏显示当前编码来源，非 UTF-8 时标黄。
写入时始终 UTF-8 无 BOM。

## 五、导出 PDF

走 WebView2 原生的 `ICoreWebView2_7::PrintToPdf`：用的是**同一个渲染引擎**，
所以导出的 PDF 与屏幕上看到的排版完全一致（含中文、表格、代码块、公式、图表），
文字仍是可选中可搜索的真文字，而不是一张截图。不引入 PDF 渲染库。

页边距不在 Rust 侧设置（全部传 0），交给 CSS 的 `@page` —— 这样手动打印时也是同一套边距，
只有一个真相来源。

## 六、启动文件传递：一个踩过的时序坑

最直觉的做法是在 Rust `setup` 里 `sleep(120ms)` 再 `emit("open-file")`。**这在真实环境会失效**：
前端启动时要实测各套正文主题的背景色，耗时不可控。一旦监听器注册晚于事件发出，
事件被静默丢弃，结果是「双击 .md 打开 → 窗口空白，且没有任何报错」。

本项目反过来做：Rust 侧把启动路径存进 `Mutex<Option<String>>`，
前端完全就绪后调用 `take_startup_file()` 主动取走（取完即清空）。
从根上消除时序竞争，与前端初始化快慢无关。

## 七、安全设计

- Markdown 内嵌 HTML 必须过 DOMPurify 才进 DOM；
  文档里连一个 `<` 都没有时跳过整树消毒（1.28 MB HTML 上约 72 ms），
  安全性来自 markdown-it 自身的转义与 `validateLink`（挡 `javascript:` 等协议）
- Mermaid 走自己的 `securityLevel: 'strict'` 消毒，不经过 DOMPurify（否则它的 SVG 会被规则误伤）
- 权限最小化：前端**没有** fs 插件的任意路径访问，文件读写全部走 Rust 命令；
  Tauri capability 只开必要的窗口权限（去装饰 / 全屏 / 拖拽）
- 写入始终 UTF-8 无 BOM

## 八、性能：冷启动与打开文件只做必要的事

策略可以概括成一句话：**首屏只加载「打开软件」这件事本身需要的东西，其余全部按需**。

| 不变式 | 守卫 |
|---|---|
| 首屏 JS 不背按需库 | `python scripts/check-build-perf.py` |
| 内置 CJK 字体按 unicode-range 分片 | `python scripts/slice-fonts.py`（带 cmap 并集断言） |
| 文档解析与渲染一致 | `node scripts/smoke-test.mjs` |

### 启动路径

1. `applyThemes()` → 注入 `@font-face`。只有小字体（西文/符号）是静态的，
   思源黑体/宋体走分片表（按家族动态 import），文楷的 194 片表更要选中才注入。
2. 默认视图是「阅读」，所以**不创建 CodeMirror**，按 `Ctrl+2/3` 时才 `import()` 进来。
3. 窗口先亮出来，**再做 IPC 往返**（注册监听、取启动文件、读盘打开文档）。
4. 「打开方式」登记与 `SHChangeNotify` 挪到窗口显示之后，而且 Rust 侧带版本戳。
5. **不预热 mermaid**：它现在是真正的动态 chunk，启动后固定 1.5 秒去预热等于把 5 MB 拉回冷启动路径。

### 打开文件与渲染

- Rust 的读/写命令是 `#[tauri::command(async)]`：同步命令跑在主线程上，读盘 + 解码会堵住事件循环
- **代码高亮不参与渲染**：markdown-it 只输出转义后的纯文本，代码块由 `IntersectionObserver`
  （±400px 预读）在滚进视口时补着色，结果按 `(语言, 代码)` 缓存。1 MB 文档的渲染因此从 113 ms 降到 25 ms
- 界面增强与标题收集合并成**一次 TreeWalker**（原来是 5 次全树查询）
- 正文超过 12 万字时给 `body` 加 `.is-longdoc`，屏外的块用 `content-visibility: auto` 跳过布局与绘制
- 渲染有 `seq` 代号，等待按需引擎期间若文档又变了，过期结果直接丢弃（每个分组一份）

### 大文件与编辑

- 字数统计改成**一趟正则**（原来是「match 中文 + replace 全文 + match 西文」，5 MB 文档 150 ms），
  并且挪到「停止输入后 + 空闲时段」，不再挂在每次光标移动上
- 编辑器的 `updateListener` 不再做 `doc.toString()`：那会在每次击键复制一整份文档

### 已知取舍

- `content-visibility` 会让浏览器原生查找（Ctrl+F）看不到尚未渲染的区域，所以只对长文档开
- 分片字体让首屏只取常用层，**字符覆盖没有任何裁剪** —— 冷门层仍随包分发
- 两栏并排时栏间是固定 50/50（栏内「源码 / 预览」的分隔条可拖拽）
